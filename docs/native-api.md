# Native API integration

The optional API module shares controllers, DTOs, pagination, validation errors,
file uploads, image sizing, page editing, translation-entry editing and bearer
API key services. Host applications expose the controllers through small
subclasses, following the admin CRUD controller pattern.

## Enable the shared infrastructure

Install `symfony/object-mapper` in the host application. The API module supports
ObjectMapper `^7.4 || ^8.0`; it is a development dependency of this bundle and an
optional runtime dependency for consumers. Applications leaving the API disabled
do not need ObjectMapper or an API-capable user.

```yaml
lexio_admin:
    default_locale: bg
    locales: [bg, en]
    api:
        enabled: true
        path_prefix: /api/v1
```

API controllers and translation-entry services reuse the bundle's existing
`default_locale` and `locales` settings. Configure these once at the root of
`lexio_admin`; enabling the API needs no additional locale configuration.
File and cached-image API URLs are generated by the bundle's existing
`FileManager`. It and API key prefixes use the shared `SITE_BASE_URL`.

`config/api.yaml` and `config/api_security.yaml` contain service definitions
loaded only when their respective features are enabled. They reference shared
settings without introducing separate API values for them.

`path_prefix` classifies API requests for error handling.
It does not rewrite controller routes. Change the host route attributes and
firewall pattern together when choosing another prefix. Matching respects path
boundaries, including API requests that fail before a route is found.

## Expose the controllers

The host imports its own API controller directory without localized URL
prefixes. The bundle provides method routes; the host supplies the class prefix.
Keep one concrete subclass per resource to avoid duplicate route names.

```php
use App\Entity\Image;
use Lexio\AdminBundle\Contract\File\ImageEntityInterface;
use Lexio\AdminBundle\Controller\Api\ImageController as BundleImageController;
use Symfony\Component\Routing\Attribute\Route;
use Symfony\Component\Security\Http\Attribute\IsGranted;

#[Route('/api/v1/images', requirements: ['id' => '\d+'])]
#[IsGranted('ROLE_USER')]
final class ImageController extends BundleImageController
{
    public function getEntityFqcn(): string
    {
        return Image::class;
    }

    public function imageEntity(): ImageEntityInterface
    {
        return new Image();
    }
}
```

`FileController` uses `getEntityFqcn()` and `fileEntity(): FileEntityInterface`.
The standard file and image DTOs also expect a readable `createdAt` timestamp.
The reusable `Repository\FileRepository` and `Repository\ImageRepository` bases
provide structured filters; host repositories select their concrete entity in
their constructor and retain application-specific queries.

`PageController` manages the bundle's `Page` and `ContentItem` entities through
`PageAdministrationInterface`; its host subclass only needs a prefix and access
rule. `TranslationEntryController` uses `TranslationCatalogInterface`; protect
the host subclass with `ROLE_ADMIN`. Translation management must be enabled for
its catalog operations.

File/image uploads and deletes, and page updates, require `ROLE_EDITOR`.
Read authorization belongs to the host's controller and firewall access rules.
Default route names remain `api.v1.file.*`, `api.v1.image.*`, `api.v1.page.*`
and `api.v1.translation_entry.*`, including when a host changes its URL prefix.

Settings, blogs, categories and tags remain application concerns. Their
controllers can extend `Controller\Api\BaseApiController` and reuse the public
interfaces under `Contract\Api`, traits under `Api\Query` and `Api\Payload`,
response envelopes, shared transformers and response helpers.

The API retains `api:list`, `api:view` and related serialization groups, snake
case response names, a default limit of 20 with a maximum of 100, validated sort
fields, locale selection, and partial-update semantics. Errors use Problem
Details JSON and preserve HTTP exception headers. Debug trace context is emitted
only when `kernel.debug` is enabled.

API response messages, validation errors and API-key command output are always
English. They do not use an `api` translation domain or translated message keys.
Request mapping uses the existing query and payload resolvers and the host's
validator. The shared API error formatter renders each violation's original
English template, parameters and plural form without translation catalogues.
Validation messages in debug exception context follow the same formatter.
No API-specific mapping subscriber or duplicate validator/resolvers are needed.
Browser/admin validation keeps its existing translations. Custom API constraint
messages must be English literals.

Select resource content with `?_locale=en` on reads and writes. For compatibility,
the API also accepts the `locale` query parameter and the JSON `locale` property.
Precedence is `_locale` query, `locale` query, JSON `locale`, then the existing
`lexio_admin.default_locale`. Languages come from `lexio_admin.locales`.

`ApiLocaleSubscriber` bridges that input into Symfony's `_locale` request
attribute after routing and before the native locale listeners. Stof/Gedmo and
the request locale are therefore synchronized before Doctrine resolves entity
arguments. Invalid locale input is reported after authorization; malformed JSON
remains the native payload resolver's responsibility. Browser routes are unaffected.
No localized API route prefixes or host listener registration are required.

API helpers preserve this request locale. Page content transformation only maps
already-loaded values: GET responses do not refresh each item or the page.
Post-write root-entity refreshes and the page manager's write operations remain
separate from read transformation. Functional fixtures must clear their entity
manager before a request when they have already loaded entities in another locale.

## Optional bearer API key security

The host user implements `Contract\Api\ApiKeyUserInterface` alongside its
existing security interfaces. The host owns the nullable, uniquely indexed,
64-character SHA-256 hash field and its Doctrine mapping.

```yaml
lexio_admin:
    user_entity_class: App\Entity\User
    api:
        enabled: true
        security:
            enabled: true
            registration_listener: true
            identifier_property: email
            hash_property: apiKeyHash
```

The default `DoctrineApiKeyUserProvider` queries the configured user entity and
properties. Set `api.security.user_provider` to another service implementing
`ApiKeyUserProviderInterface` for a different persistence model. A custom
provider does not require `user_entity_class`.

Account-state rules belong to the host's Symfony security configuration. The
starter's `App\Security\ApiUserChecker` rejects blocked accounts during
authentication, producing 401. Its `App\Security\Voter\ApiAccessVoter` requires
`ROLE_USER` and either a confirmed email or editor permissions, including roles
inherited through the role hierarchy. Authenticated denials produce the shared
403 Problem Details response. The voter is registered by host autoconfiguration.

Keep firewall order, the Symfony user provider, role hierarchy and access rules
in the host. Place the stateless API firewall before the browser firewall:

```yaml
security:
    firewalls:
        api:
            pattern: ^/api/v1(?:/|$)
            stateless: true
            provider: app_user_provider
            user_checker: App\Security\ApiUserChecker
            entry_point: Lexio\AdminBundle\Security\ApiAuthenticationHandler
            access_denied_handler: Lexio\AdminBundle\Security\ApiAccessDeniedHandler
            access_token:
                token_handler:
                    id: Lexio\AdminBundle\Security\ApiKeyHandler
                failure_handler: Lexio\AdminBundle\Security\ApiAuthenticationHandler
        # Configure the host browser firewall after api.
    access_control:
        - { path: ^/api/v1(?:/|$), roles: API_ACCESS }
```

`API_ACCESS` is the host voter's permission. Keep it as the single access-control
attribute: listing it alongside `ROLE_USER` would allow the default affirmative
decision strategy to bypass a voter denial. Applications without account-state
restrictions can retain `ROLE_USER` and omit the custom checker and voter.

Symfony's native access-token authenticator extracts `Authorization: Bearer`.
The API handler resolves the stored hash and returns the host user. Browser
sessions do not authenticate this stateless firewall.

`ApiAuthenticationHandler` serves both the firewall entry point and the
authentication failure handler. Missing and invalid credentials receive the
same 401 Problem Details response with a `WWW-Authenticate: Bearer` header.

`UserApiKeyListener` is registered only when `registration_listener` is enabled.
It handles the existing `UserHasRegistered` event, resolves its affected user
identifier through the provider and preserves an existing credential. The
registration listener and backfill store hashes and discard the raw keys.

The bundle registers `lexio:api-key:issue <email>` and
`lexio:api-key:backfill`. The historical `email` argument contains the configured
user identifier. Issue displays the raw key once and immediately invalidates the
previous key; backfill only generates missing credentials. Raw keys contain
32 hexadecimal characters with an optional site-derived prefix; only their
64-character SHA-256 hashes are persisted.

The starter preserves `app:api-key:issue` and `app:api-key:backfill` as command
aliases in its services configuration. Other hosts can add their own aliases:

```yaml
services:
    Lexio\AdminBundle\Command\ApiKeyIssueCommand:
        autowire: true
        tags:
            - { name: console.command, command: 'lexio:api-key:issue|app:api-key:issue' }
```

## Migrating an existing host

1. Replace shared API DTO, transformer, response, exception and service imports
   with their bundle namespaces. The query and payload interfaces now live under
   `Lexio\AdminBundle\Contract\Api`.
2. Replace file, image, page and translation-entry implementations with the
   subclasses described above. Keep host entities, factories, fixtures and
   application-specific endpoints.
3. Enable the core API; enable API key services separately if needed. Implement
   the optional user contract and host account checks through Symfony's user
   checker and voter, then update the API firewall references.
4. Remove the old host exception/confirmation subscribers, key listener and key
   commands so events are handled once. Use `ApiRequestMatcher` in any host
   subscriber that must distinguish JSON API responses from browser redirects.
5. Update fixture/test imports, preserve command aliases as needed, warm the
   cache, verify routes and run host integration tests.

Existing key hashes and user tables remain unchanged by the extraction.
The signed translation-package endpoints under `/api/translations` retain their
own authentication and are outside the versioned bearer API.
